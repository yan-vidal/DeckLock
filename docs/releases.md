# Release procedure

This document records the procedure. Publishing any version requires the user's explicit approval.

1. Define the scope and review CHANGELOG.md. Label PRs enhancement, bug, documentation, maintenance or dependencies; unmatched PRs remain included in Other changes. Review user-facing notes rather than treating commit messages as documentation.
2. Update Cargo.toml/Cargo.lock to the full X.Y.Z version and reset Arch pkgrel to 1 for an application release. A packaging-only rebuild increments pkgrel without changing Cargo; its tag is vX.Y.Z-rN. The Fedora spec and the Ubuntu control file fix their own package revision at 1, so a packaging-only rebuild currently revises the Arch package alone and a rebuild of the RPM or DEB needs those recipes bumped by hand. A release candidate keeps a SemVer prerelease version such as 0.3.0-rc.1 and tags vX.Y.Z-rc.N. Legacy v0.1/v0.1-r2 releases retain their existing names and assets.
3. Run scripts/check --all and require the GitHub checks, including Real Wayland and PAM for every target. Package verification includes the real packaged CLI, guide payload, full version names, tag rejection and changelog extraction. PR artifacts are candidates, not published releases.
4. Record the VM evidence for installing/reinstalling the candidate package, preserving configuration, real Sway lock/unlock and real PAM acceptance, denial and lockout. Each packaged distribution has its own target, so this evidence exists per distribution rather than being inferred from Arch. This removes those controlled checks from the manual checklist; it does not cover upgrading from every prior version. Keep device-specific keyboard/controller behavior, normal/rest media, physical suspend, GPU and recovery on other compositors as explicit limits or recorded manual validation. Never describe preview or VM tests as physical-device validation.
5. Once the release is approved, replace Unreleased in its changelog heading with the actual release date. Preview the summary with python3 scripts/release-notes.py; validate publication readiness with --require-date. Update README installation examples to the soon-to-be-published full version as part of the release PR, not while that download does not exist.
6. Merge through the protected PR flow. Confirm main checks and tag the reviewed commit with vX.Y.Z (or the packaging-revision tag). Never move a published tag or replace an asset.
7. The tag workflow reruns tests/builds, verifies ancestry/version/checksums and the dated changelog, then publishes the release with the Arch, Fedora and Ubuntu packages, their payload archives, the PKGBUILD and one combined SHA256SUMS. A publish does not run unless every target's package contract and VM gate passed in the same run, and every target is verified against its own build-time checksums before anything is uploaded. The channel follows the source version: a SemVer prerelease version publishes as a GitHub pre-release and keeps the experimental prerelease line in the summary, while a plain X.Y.Z version publishes as a full release and lets GitHub assign the Latest badge by date and version. The reviewed summary precedes GitHub's generated PR references. Confirm the assets/downloads and notes after publication.

There is no automatic release on PR creation or merge. SHA256 checksums detect changed bytes; they are not signatures. Current CI records source and linked-library provenance, but does not claim bit-for-bit reproducibility or a security audit.
